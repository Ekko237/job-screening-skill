# 机会扫描：这份简历还能投哪些方向

两个场合用：**首次建档的第 3 步**，以及用户直接问「我适合什么岗位」「还能投什么」。

目的不是列一堆岗位名，而是回答一个问题：
**这份简历的形状，在招聘市场上对应哪些职位，其中哪些他自己没想到。**

---

## 方法：从证据反推，不要从岗位名正推

❌ 错的做法：列出「产品经理、运营、市场、数据分析、项目管理……」然后逐个说他行不行。
这是把招聘网站的分类抄一遍，没有信息量。

✅ 对的做法：**先把简历拆成证据，再看这些证据组合起来在市场上值什么。**

### 第 1 步：把简历拆成 5–8 条"能力证据"

一条证据 = 一件具体做过的事 + 可验证的结果。例如：
- 「独立把一个产品从想法做到上线并有真实用户」
- 「把一个渠道的量从 0 做到 X」
- 「做过 N 个页面/素材并有转化率数据」
- 「在一个 X 人的团队里负责 Y」
- 「用 A 技术栈实际交付过东西」

**没有结果的不算证据**（「参与了某项目」不是证据）。
这一步做完，他画像的"形状"就出来了——通常是一句话，比如
「一个人从判断需求到上线全做完的人」或「在成熟流程里把复杂项目推下去的人」。

### 第 2 步：每条证据映射到岗位序列

同一条证据在不同序列里的价值不一样。逐条问：**哪些岗位的 JD 会把这条当成硬通货？**

常见映射（**只是提示，不要当清单套**）：
| 证据类型 | 直接对口 | 也吃这套但他可能没想到的 |
|---|---|---|
| 独立 0→1 做出并上线产品 | 产品经理 | 新业务/孵化岗、创业公司早期成员、解决方案 |
| 渠道从 0 做到规模 | 增长 / 运营 | 出海产品经理、商业化产品、市场策略 |
| 工具/自动化把重复劳动干掉 | 效率工具产品 | 内部系统产品经理、业务中台、AI 应用落地 |
| 有技术栈且真交付过 | 技术产品经理 | 解决方案架构、售前、开发者关系（DevRel） |
| 内容/社区从 0 起量 | 内容产品 / 社区运营 | 创作者生态、平台治理、海外社媒 |
| 在多人团队里推成一件事 | 项目管理 | 管培生、战略、业务分析 |

第二列是这一步的**真正产出**——它们是用户自己不会去搜的关键词。

### 第 3 步：过一遍他的硬约束

映射出来的方向，逐个拿档案里的硬约束筛（城市、不投的序列、学历、到岗时间）。
**过不了的直接划掉并说明原因**，不要留在清单里让他空欢喜。

### 第 4 步：给每个方向标"缺什么"

一个方向能不能投，不只看有什么，还看**缺的那块会不会直接被刷**。每个方向写一行：
- **可投**：现有简历就能论证
- **可投但会被追问**：能论证，但面试会卡在某个点上（写明是哪个点）
- **暂时不行**：缺的是硬门槛（学历、专业、某个必须的经验），写明缺什么

---

## 输出格式

```
## 你这份简历的形状
<一句话画像> + <3–5 条能力证据，每条带结果数字>

## 直接对口（你已经在投的）
- <方向>：<简历里哪一段支撑> —— 可投

## 你可能没考虑过的（重点看这几个）
- <方向>：<为什么这份简历吃得开，引用具体那一段> —— 可投 / 可投但会被追问 <哪一点>
- <方向>：...

## 不建议的
| 方向 | 原因 |
|---|---|
| <名> | <被硬约束挡了 / 缺硬门槛> |

## 建议的投递顺位
<给一个排序 + 一句理由。明说这只是建议，让他自己定>
```

---

## 纪律

- **每个方向都必须能指回简历里的具体一段。** 指不回去的不要写——那是在给通用职业建议，
  不是在看他的简历。
- **不要为了让清单显得丰富而凑数。** 三个扎实的方向比八个泛泛的方向有用。
- **不要编造经历**，也不要把"他可能会喜欢"当成"他能投得上"。
- 只在作品集/个人网站上、投递版简历里没有的经历，
  可以用来发现方向，但要**明确标注**「这段简历上没有，投这个方向前得想清楚怎么让 HR 看到」。
